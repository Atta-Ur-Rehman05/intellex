# ADR-0004: Object Storage for Uploaded Documents

* **Status:** Accepted
* **Date:** 2026-08-17
* **Decision Owners:** Intellex Engineering
* **Related:** ADR-0001 Modular Monolith Architecture, ADR-0002 Technology Stack, ADR-0003 PostgreSQL + pgvector

---

## 1. Context

Intellex allows users to upload knowledge sources such as:

* PDF
* DOCX
* TXT
* Markdown
* other supported document formats

These files can be significantly larger than normal relational records and must be stored independently from application metadata.

Storing complete document binaries directly in PostgreSQL would unnecessarily increase database size, backup requirements, and database I/O.

Intellex therefore requires a dedicated object-storage layer.

---

## 2. Decision

**Original uploaded documents will be stored in S3-compatible object storage.**

PostgreSQL will store the document's metadata and a reference to its object-storage location.

Architecture:

```text id="d2ef37"
                User
                  │
                  ▼
               FastAPI
                  │
          ┌───────┴────────┐
          ▼                ▼
     PostgreSQL       Object Storage
      Metadata          Actual File
```

Example:

```text id="3jp7ik"
PostgreSQL

documents
├── id
├── workspace_id
├── filename
├── content_type
├── size
├── storage_key
├── status
└── timestamps
```

Object storage contains:

```text id="cnk76r"
workspaces/
└── {workspace_id}/
    └── documents/
        └── {document_id}/
            └── original-file.pdf
```

---

## 3. Storage Responsibilities

### PostgreSQL owns

* document identity
* workspace ownership
* filename
* MIME/content type
* file size
* storage key
* processing status
* timestamps
* document-level metadata
* authorization relationships

### Object Storage owns

* original file bytes
* large binary objects
* object lifecycle

PostgreSQL remains the source of truth for document metadata.

---

## 4. Object Storage Choice

Intellex will use an **S3-compatible storage interface**.

For local development:

```text id="lq2t1x"
MinIO
```

may be used.

For production, the implementation may use:

* Amazon S3
* another S3-compatible provider

The application should interact through a storage abstraction rather than embedding provider-specific logic throughout business modules.

---

## 5. Upload Flow

The document upload lifecycle will follow this general pattern:

```text id="z1n7wa"
User
 │
 ▼
API
 │
 ├── Authenticate user
 ├── Validate workspace access
 ├── Validate file type/size
 │
 ▼
Object Storage
 │
 ▼
Create/Update Document Metadata
 │
 ▼
Queue Processing Job
```

Document processing is handled separately according to the background-processing architecture defined in ADR-0005.

---

## 6. Access Control

Object storage access must not bypass Intellex authorization.

A user must not be able to access another workspace's files simply by knowing or guessing an object key.

Application-level authorization must verify:

```text id="6b7z2h"
Authenticated User
       │
       ▼
Workspace Membership
       │
       ▼
Document Access
       │
       ▼
Object Retrieval
```

Object keys should therefore be treated as identifiers, **not security credentials**.

Where appropriate, the application may provide controlled or time-limited access to objects rather than exposing permanent public URLs.

---

## 7. File Validation

Uploaded files must be validated before being accepted for processing.

Validation should include, where applicable:

* supported file type
* MIME/content type
* file size
* filename constraints
* safe storage key generation

The system should not trust the client-provided filename or MIME type as the sole validation mechanism.

Uploaded content should be processed safely and isolated from application execution.

---

## 8. Object Key Strategy

Object keys will be generated by Intellex rather than directly trusting user-provided filenames.

A logical structure such as:

```text id="4gq7zx"
workspaces/{workspace_id}/documents/{document_id}/{generated_name}
```

will be used.

This provides:

* workspace-level organization
* predictable ownership
* reduced filename collision risk
* separation between user filenames and storage identifiers

User-facing filenames remain metadata in PostgreSQL.

---

## 9. Document Lifecycle

The document record and object should have a defined lifecycle.

Conceptually:

```text id="c2a4qz"
Created
   │
   ▼
Uploaded
   │
   ▼
Processing
   │
   ▼
Ready
   │
   ├── Failed
   │
   └── Deleted
```

Deletion must consider both:

1. PostgreSQL metadata
2. Object-storage content

The system should avoid leaving orphaned objects when documents are permanently deleted.

---

## 10. Failure Handling

Object storage and PostgreSQL operations may fail independently.

The implementation must therefore account for partial failures.

Examples:

```text id="w0b6pz"
Database succeeds
Object upload fails
```

or:

```text id="6o5n0a"
Object upload succeeds
Database operation fails
```

The document lifecycle and background processing system must provide mechanisms for detecting and recovering from these inconsistent states.

---

## 11. Backup and Durability

Object storage is responsible for durable storage of original files.

Production deployment should use the storage provider's appropriate:

* durability
* replication
* backup
* lifecycle
* retention

capabilities.

Database backups alone are not sufficient to recover Intellex documents because the original binaries live outside PostgreSQL.

---

## 12. Consequences

### Positive

* Keeps PostgreSQL focused on structured data
* Suitable for large files
* Easier horizontal storage scaling
* Better separation of responsibilities
* S3-compatible production path
* Simple local development with MinIO

### Negative

* Introduces an additional infrastructure dependency
* Requires storage-specific failure handling
* Requires object lifecycle management
* Database and object storage must be backed up independently
* Authorization must be enforced carefully

---

## 13. Alternatives Considered

### Store files directly in PostgreSQL

Rejected because large binary objects would unnecessarily increase database size and operational overhead.

### Store files on the application server filesystem

Rejected because local filesystem storage is unreliable for horizontally scaled or containerized deployments and complicates persistence and recovery.

### Cloud-provider-specific storage API

Rejected initially in favor of an S3-compatible abstraction to reduce unnecessary provider coupling.

---

## 14. Future Considerations

Object storage architecture may evolve to support:

* multipart uploads
* resumable uploads
* presigned URLs
* virus/malware scanning
* automatic lifecycle policies
* archival storage
* document versioning
* retention policies

These should be introduced based on actual product and operational requirements.

---

## 15. Final Decision

Intellex will store **original uploaded documents in S3-compatible object storage** and store their **metadata, ownership, authorization relationships, processing state, and storage references in PostgreSQL**.

The object-storage layer will remain separate from the document-processing and RAG layers, providing a clean boundary between:

```text id="x5v7s0"
Application Metadata
        │
        ▼
    PostgreSQL

Original Files
        │
        ▼
 Object Storage

Processed Knowledge
        │
        ▼
PostgreSQL + pgvector
```

This architecture provides an appropriate foundation for secure, scalable document storage without overloading the relational database.
